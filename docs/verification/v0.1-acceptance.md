# v0.1 verification record (US-020)

What was verified, how, and what is still unverified. This closes US-020's deployed-path and
offline integration checks; it changes no app code.

**Environment limit.** This machine has no browser binary and no browser automation, and the
project forbids adding one (no dependency beyond `typescript`, no test framework). So the
device checks were substituted, strongest first:

1. the real `sw.js` in a Node `vm` over `CacheStorage`-shaped fakes, with `fetch` bound to the
   **real** local HTTP server;
2. the real zero-argument `boot()` over a DOM-shaped fake and a browser-shaped hash history,
   playing all three Games against the served app;
3. a fresh boot whose **only** `fetch` is the primed cache — the offline relaunch — playing all
   three Games and opening every statistics view;
4. the committed, dependency-free suite (`npm test`, 125 sanity cases).

The one thing none of these can close is a physical device (see Residual risks).

## How to reproduce

```sh
ln -s "$PWD" /tmp/serve/giocco
cd /tmp/serve && timeout 180 python3 -m http.server 8001 &   # the documented local server
# the harness (not committed: it was scratch, so treat these as a recipe, not a script that
# still exists) starts the server, polls readiness, runs the check, then stops the server
```

The one-off scratch harness lived in `/tmp/us020/` (an un-ref'd watchdog and bounded polls, so a
stuck round failed loudly instead of hanging); it was never committed and is not reproduced here.
The durable parts of the same checks live in `tools/sanity.mjs` and run offline — the deployed
shape as a case, and the worker, boot and round behaviour behind `swHarness()`,
`bootHarness()` and `withFakeDocument()`/`withFakeTimers()`.

## 1. The deployed path (`/giocco/`)

Served a symlink of the worktree as `/giocco/` on :8001 and crawled it the way a browser does.

- `index.html`, every `href`/`src` in it, `styles.css` (`text/css`), `manifest.webmanifest`
  (`application/manifest+json`), `sw.js` (`text/javascript`), `js/app.js` (`text/javascript`) —
  **all 200**, all **relative**.
- The whole module graph — 11 modules (`js/app.js`, `engine.js`, `registry.js`, `router.js`,
  `storage.js`, `ui.js`, the three Game modules, `js/lib/roundLoop.js`, `js/lib/charts.js`) — every
  import specifier relative, every module 200 `text/javascript`. Nothing resolves outside `/giocco/`.
- Registry order on the served app: `verbi-presente → verbi-presente-rivela → nomi-plurale`.
- Both corpora 200 `application/json` (`verbi-presente.json` served to both verb Games,
  `nomi-plurale.json`); the served bytes equal the local file.
- `.nojekyll` present and 200 (0 bytes).
- `manifest.webmanifest`: `start_url: "./"`, `scope: "./"`, `display: "standalone"`; the three
  icons (`192`, `512`, `maskable 512`) relative and 200 `image/png`.
- `sw.js` sits at the **root of the subpath**, so its scope is `/giocco/`; it is a classic
  worker (no `type: 'module'`), `CACHE` is exactly `giocco-v1` and `SHELL` is exactly
  `['./', './index.html', './styles.css', './manifest.webmanifest']`.
- Development gates: no app URL (HTML references, module graph, manifest, worker) is under
  `tools/` or `node_modules/`, no module imports either, and neither appears in the precache
  list. `package.json` is not app runtime.
- Server log: **0** 404s during the whole run. The server was stopped afterwards
  (`run.sh` kills it; `pgrep` finds nothing left).

## 2. Offline: first online load, then kill and relaunch

The real worker ran against the real server, with every app URL **dispatched through the fetch
handler** the way a controlled page's requests arrive.

- `install` precached exactly the four shell URLs.
- One pass of the app graph through that handler — 4 shell URLs, 11 modules, 4 icons and the 2
  distinct corpus URLs — left **21 entries** in `giocco-v1` and nothing else; no gate URL is
  cached.
- Then a **new** worker instance over the same cache storage, with the network switched off
  (every fetch rejects) and `activate` run: `./index.html` was answered from the cached shell
  with **zero** network attempts (navigation never waits on a doomed request), and every other
  URL — app code network-first, corpora/icons stale-while-revalidate — attempted the network,
  failed, and still returned **byte-identical to the served copy**. 20 URLs, the 2 corpora
  included.
- A fresh `boot()` whose only `fetch` is the primed cache loaded all three Games' content, and a
  full round was played in each (10/10, summary, statistics, Summary back), with **zero** cache
  misses. That is the "kill/relaunch while offline" step, minus the device.

**What this does not prove — the first load.** A pass through the handler is not the same request
sequence as a real first visit. `index.html`'s one module entry fetches `js/app.js`, and its
static imports fetch the whole Game graph, *before* `js/app.js` runs and registers `./sw.js`; the
corpus fetches it then awaits race the worker's install → `skipWaiting()` → `activate` →
`clients.claim()`. So a first-ever visit is guaranteed to cache the four precached shell URLs and
may cache nothing else: the module graph and the corpora reach `giocco-v1` on the first
**controlled** load, i.e. the next one. This record cannot close that window, and v0.1's design has
no warm list or message channel to close it with (`docs/design/architecture.md` § Service worker,
`AGENTS.md`). Residual risk 6 is the device step that would settle it.

## Residual risks (non-blocking)

1. **No physical device.** Airplane-mode play, an installed-app launch (iOS Safari standalone,
   Android Chrome), the safe-area insets, focus order and hit targets under a thumb, and how the
   inline-SVG charts look at rendered size are still only verified by proxy. This is the one
   US-020 acceptance item a human must eventually close on real hardware; everything that can be
   checked without a browser is checked above and in the suite.
2. **No browser's own HTTP cache or install timing.** `skipWaiting()`/`clients.claim()` races,
   a second open tab, and the file:// insecure-context path were reasoned about and unit-checked,
   not observed in a browser.
3. **The real host.** The `/giocco/` subpath was verified through a local symlink
   (`python3 -m http.server`), not on GitHub Pages. Pages' `Cache-Control` on `sw.js` is what
   `{ updateViaCache: 'none' }` exists for; it is not exercised by the local server.
4. **Deploy freshness.** That a redeploy's new app code wins over a cached copy rests on
   network-first for `js/**`/CSS/the manifest and on `activate` dropping every non-current cache;
   both are covered by suite cases, not by two consecutive deploys.
5. **The served tree includes `tools/` and `node_modules/`** when the repository root is served
   (as the docs prescribe). Neither is app runtime, imported, or precached — the worker only
   answers same-origin GETs it is asked for — but a clean deploy could exclude them. Inert, and
   out of v0.1's scope.
6. **The window between the first load and the first controlled load.** The four shell URLs are
   in `giocco-v1` after install, but the module graph and the corpora are requested before the
   worker claims the page (`docs/verification/v0.1-acceptance.md` § 2, "What this does not
   prove"). The device step that settles it: load the app online **twice** (a reload after the
   first load is enough for the worker to be in control), then enable airplane mode, play all
   three Games, kill the app and relaunch it offline. If a single load is enough on the target
   device, this risk closes; if it is not, the app graph genuinely needs the second load and only
   a warm list (excluded from v0.1 by design) would remove it.
